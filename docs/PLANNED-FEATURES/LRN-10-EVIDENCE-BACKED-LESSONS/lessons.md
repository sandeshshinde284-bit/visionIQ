# Lessons (LRN-10)

Repeated failures become **lessons**: one reusable unit of knowledge supported by several tickets
(master design §6.10, §8.9, §6.20). Run once per schedule:

    PYTHONPATH=src/VisionIQ.Intelligence python -m app.knowledge.lessons_cli

Uses the intelligence database login (`DB_INTELLIGENCE_*`): it reads evidence and writes only the
`knowledge` schema. `LESSON_DEFECT_TYPES` (default `Bug`) lists the work-item types that count as defects.

## Qualification rule

| Rule | Detail |
|---|---|
| Observation | A defect ticket (not deleted) with an **explicit** fix link that a review has not disputed, plus the files that fix **changed** (`evidence.fix_change_sets`), ignoring build/lock/doc noise |
| New lesson | At least **2 distinct current Bug tickets** with explicit undisputed fix links and changed-file overlap (Jaccard ≥ **0.5**) in the **same repository**, plus matching normalized failure symptoms from the source title/reproduction text (symptom Jaccard ≥ **2/3** and at least **3 distinctive shared terms**). Diagnostic symptoms are taken from a **current, ACL-matched, published and redacted LRN-08 index chunk** (not raw source). Synthetic metadata fixtures may include explicitly redacted title/repro fields, but production LRN-03 metadata does not store title text. Same changed file alone never qualifies |
| Join | A new observation joins exactly one **candidate** lesson only when it independently matches at least two existing distinct-ticket members on code and symptoms; reviewed lessons require another human review, while disputed/retired lessons cannot silently absorb similar evidence |
| Ambiguous | Several qualified lesson matches, or a new observation for a reviewed lesson → `HUMAN_REVIEW` (not joined). Missing/generic symptoms, missing current published index data, or matches against disputed/retired lessons → `WAIT_FOR_EVIDENCE` |
| Cause | Always `unverified`; only a named human can mark a lesson reviewed or its cause verified (the database enforces this) |
| Revert | A later revert of any supporting fix appends a **disputed** revision; earlier revisions are kept (the database rejects edits and deletions) |

Thresholds, token normalization and noise patterns are transparent constants in `app/knowledge/lessons.py` (`MIN_TICKETS`, `OVERLAP`, `SYMPTOM_OVERLAP`, `MIN_SHARED_SYMPTOM_TERMS`, `NOISE`, `STOPWORDS`). The matching is deterministic, conservative lexical corroboration: **not** a semantic embedding model, verified root-cause inference or assertion of an effective fix. It may miss genuinely similar failures described with very different words; such evidence remains ungrouped for human judgment. Only normalized diagnostic tokens are used in-memory; raw ticket descriptions are not added to lesson-observation rows. A ticket without a current redacted, published description/repro chunk is not auto-qualified. This makes a current LRN-08 snapshot a dependency for this strengthened qualification path, although the base LRN-10 story previously depended only on LRN-04.

## Where things are

| Table | Content |
|---|---|
| `knowledge.lesson_patterns` | One row per lesson and its latest revision number |
| `knowledge.lesson_revisions` | Append-only versions: status (candidate / reviewed / disputed / retired, master design §6.6 stage 8; an OKF export maps reviewed → current and retired → stale), cause status, title, signature files, supporting observations, decision, rationale, generated by, verified by, OKF path/revision (for a later OKF export) |
| `knowledge.lesson_memberships` | Which observation supports which lesson |
| `knowledge.lesson_observations` | The evidence each observation was built from |
| `knowledge.lesson_decisions` | Every decision with its rationale: CREATE_NEW, LINK_EXISTING, REVISE_EXISTING, HUMAN_REVIEW, WAIT_FOR_EVIDENCE |

Runs are deterministic and idempotent (same evidence, same lessons; a repeated decision is not re-logged)
and serialized with an advisory lock.

## Change only on proof (LRN-13)

A lesson gets a **new version only when evidence materially changes**: it becomes **disputed** (a
supporting fix was reverted) or its file signature changes materially (overlap with the previous
signature below `MATERIAL_SIGNATURE_OVERLAP` = 0.8). A ticket joining, recurrence counts and "last
seen" never create a version (master design §6.10).

Show any lesson's timeline (read-only, `DB_API_*` login), e.g. to replay a real fix-then-revert:

    PYTHONPATH=src/VisionIQ.Intelligence python -m app.knowledge.lesson_history            # list
    PYTHONPATH=src/VisionIQ.Intelligence python -m app.knowledge.lesson_history <pattern>  # timeline

CI saves a replayed fix-then-revert as `lesson-replay.json` in the `learn-evidence-<commit>` artifact.

## knowledge.changed events

Every index update and removal, new lesson and lesson revision writes a row to
`knowledge.change_events` **in the same transaction** as the change (transactional outbox). A publisher
that drains unpublished rows to Pub/Sub and sets `published_at` is FND-06 infrastructure.


## Qualification safety and rollout (LRN-10 strengthening)

- Three unrelated bugs that modify one shared service file must remain observations, not become a false common lesson.
- Same symptom but unrelated changed files also must not merge. A generic title, missing title or missing source-verified access must not qualify.
- Two fixes on the same defect ticket count as **one defect**, not two independent confirmations. The grouping is pairwise-corroborated to avoid transitive chaining through a hub file.
- Previously approved/reviewed lessons are never silently expanded. A new member requires recorded `HUMAN_REVIEW`; history and verification remain human-controlled.
- Disputed or retired patterns are not automatically re-created as a fresh candidate from the same corroborated evidence. A revert still appends a disputed revision.
- **Existing legacy lessons are not retroactively deleted, merged or reclassified.** Existing memberships must be reviewed before claiming the stronger rule applies to older lessons; reindexing is not a substitute for a human revision audit.
- A lesson is still a candidate with an unverified cause, even if all code paths and symptoms agree. No code or AI should say \"same root cause\" without independent verification.

### Safe validation

Run `tests/intelligence/test_lessons.py` as pure unit tests, then use the guarded disposable PostgreSQL runner for `tests/intelligence/test_lessons_db.py`, `tests/intelligence/test_kb_readiness_db.py`, `tests/intelligence/test_retrieval_db.py` and `tests/intelligence/test_lrn13_db.py`. Keep the published Genoa Kiosk index read-only. A passing fixture suite establishes **local behavior only**, not production classification accuracy. Review real source tickets for false-positive and false-negative rates before tuning thresholds.

LRN-05: At-Least-Once Webhook Processing

🟢 Success Path

Event arrives → TryClaimAsync() → INSERT succeeds → token issued

Handler re-fetches source data (using source auth). Writes to storage. CompleteAsync(token) marks it done. Future retries of the same (source_id, event_id) return AlreadyCompleted.

🟡 Worker Crash (Lease Expires)

Event in processing → Worker dies → 5-minute lease expires → Different worker picks it up

TryClaimAsync() sees the lease expired, updates with new token and new 5-minute expiry, increments attempt_count. Handler re-runs. If it succeeds, the event completes. If it fails again, lease expires and another worker retries.

🔴 Poison Event (Dead-Letter)

Event fails repeatedly → attempt_count reaches 5 → DeadLettered

TryClaimAsync() returns DeadLettered status. Event stays in the inbox table with last_error_code set. Operator or reconciliation process investigates. The event is not retried automatically, preventing infinite loops on broken data.

🔄 Conflict (Different Source Data)

Same event_id arrives with different provider_kind, native_id, or source_revision

TryClaimAsync() compares (source_id, event_id) lookup row to incoming claim. If they differ, returns IdentityConflict. Operator must investigate: did the webhook system restart and reinterpret the event? Is it a data quality issue in the source?
